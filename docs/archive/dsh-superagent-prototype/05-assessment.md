### 三个失败的具体归因

1. **`tests/runtime.spec.ts` 两个环境恢复用例。** 测试断言 `process.env.GIT_CONFIG_GLOBAL` 在 stop 后为 `undefined`，但本归档是在**运行中的 dsh-superagent worker 环境**里执行测试的，该环境本身设置了 `GIT_CONFIG_GLOBAL`（指向部署的 `worker-gitconfig`）和 `GIT_CONFIG_NOSYSTEM=1`，`PATH` 首位是 `worker-bin`。测试恢复的是“进入测试前的值”，因此不可能变成 `undefined`。清理这两个变量和 `worker-bin` PATH 后，这两个用例通过。
2. **`tests/sources.spec.ts` 的 Feishu event consumer 用例。** 整文件运行时，健康状态是 `ready: Listening for bot events`，而不是期望的 `error: ... JSON`；单独运行该用例时通过。这说明该用例对“ready 行与畸形 JSON 行的到达顺序”敏感：后来到达的 `[event] ready` 会覆盖先前的错误状态。它更像测试隔离/时序问题，但也暴露了健康状态“后到的 ready 覆盖先前的 error”这一行为。
3. 上述两个环境用例在清理后通过，Feishu 用例仍失败一次；因此干净环境下是 1,196/1,197，而不是全绿。

**结论：** 该测试套件在正常机器上很可能接近全绿，但**不是对运行环境完全隔离的**，也不应把“全绿”当作本次归档的前提。上游自己声明这是研究代码。

## 2. 值得借鉴的设计

### 2.1 把“注意力”当成一等设计指标

大多数 agent 项目优化的是能力（能做什么），这个项目同时优化“不做什么”：

- 只在被请求或被书面规则允许时行动；
- 只在人需要行动或结果可用时说话；
- 一次只问一个具体问题；
- 进度内部记录，不刷屏；
- 面板默认安静，健康状态不占空间；
- 文档本身按注意力成本删减。

这套约束直接塑造了架构：`observe` 默认模式、订阅扇出、结构化 `human_action`、100 词上限、review 线程静默 resolve、未完成 PR 不 announce。它把“减少噪音”从提示词口号变成了默认行为。

### 2.2 确定性 Gate + 模型 Assessment 的分层

授权不是“让模型看情况”，而是：

1. 代码先做确定性判断：名单、是否 @、接收范围、准入表、accept mode、bot 身份；
2. 只有推断候选才进入模型评估；
3. 模型评估被结构化：逐规则判定、direction 三事实、证据、worktree name；
4. 代码再次校验：规则是否齐全、是否命中、是否 `auto`、Mandate 是否仍有效。

这样模型只在“语义判断”上发挥作用，权限边界不交给模型自由发挥。

### 2.3 单写入者 + 事务 + 持久化副作用

- Engine 是唯一写领域状态的地方；
- 每个命令一个事务；
- 外部副作用先入队、提交后执行；
- outbox 回执保证消息不重复、按会话有序；
- 失败有退避、健康、暂停、恢复；
- 重启后能恢复未完成的 Assignment 和未投递的 Input。

这比“在内存里存状态、失败就重来”的 agent 框架可靠得多，也是该原型最接近生产工程的部分。

### 2.4 两个角色的强隔离

主 Session 只路由，worker 只执行。两者：

- 不同 preset；
- 不同工具集；
- 不同提示词；
- 不同上下文预算；
- 不同等待策略。

好处是主 Session 不会被代码细节污染，worker 不会被其他工单干扰。代价是两套提示词、两套工具和跨 Session 消息协议，但这是值得的复杂度。

### 2.5 订阅：上下文与授权分离

订阅让后续讨论自动到达工单，不需要每次 @；但它**不授予新权限**。人的跟进由 worker 决定归属，超出范围就 hand-back；只有所有拥有者都放手后才回到 Eval。这个模型比“每条消息都重新评估”更省注意力，也比“所有消息都自动执行”更安全。

### 2.6 提示词版本化与可覆盖

- 团队可改三个段落和全部内置部分；
- 保存记录默认基线和修订号；
- 升级时保留团队文本，标记默认变化；
- 环境段/策略段动态生成；
- 覆盖等于默认时自动移除，跟随未来默认；
- 模板占位符校验，不静默截断。

这让提示词可以像代码一样审查、回滚和升级，而不是散落在字符串里。

### 2.7 Source 插件协议

`SourceKind` 把“新增一个来源”拆成清晰的 11 步：事件映射、配置 schema、Trigger 翻译、scope、Channel、Thread context、Policy、环境变量、插件入口/循环、构建注册、测试。cookbook 给出完整可运行的 webhook 示例。对于需要接入新聊天/工单系统的团队，这是可直接复用的设计。

### 2.8 文档与测试互相约束

- 编号文档只向后链接；
- 模块表和测试表必须完整；
- 每个 class 有 JSDoc；
- 模型可见表面有一致性测试；
- 中英文、样式、无 import cycle 都有测试；
- 服务脚本用假 `ps`/`tmux`/`dsh` 测。

这套“文档即测试”的做法，比“写一份架构文档然后任其腐烂”更可持续。

### 2.9 运维可用性

- `scripts/dsh-superagent` 有清晰的退出码（0/1/2/3）和 `--respect-stop`；
- 小时检查提示词区分“可重启”和“需要人”的错误；
- 健康板按责任分组；
- setup 问题直接链接到修复设置；
- 管理 API 有稳定的路由契约和错误码；
- 升级有备份、迁移、回滚说明。

对研究原型来说，运维文档的完成度相当高。

## 3. 风险、限制与未解问题

### 3.1 安全隔离不足（最重要）

- Executor 以操作员 OS 用户、`danger-full-access` 运行，能读操作员 home、按绝对路径执行任意程序；
- `worker-bin` shim、blocked commands、`worker-gitconfig` 是默认值与便利，不是安全边界；
- 文档明确建议“要隔离就用专用 OS 账号”；
- 单进程、单仓库、SQLite 目录锁，不是多租户架构。

**判断：** 适合受信任的单团队、单仓库内部试点；不适合多租户、不可信仓库或高风险环境。

### 3.2 提示词规则与代码强制之间有缝隙

不少关键行为只由提示词约束：

- 主 Session“不读代码”是提示词规则，不是工具限制（它仍有 `bash`/`read`）；
- 合并条件、review 轮数、Before/After 证据、给人署名等由 Delivery/Communication 提示词治理；
- 自动审查者识别依赖团队在提示词里列出账号；
- 主 Session 的“不等待”有代码守卫，但“不调查 blocker”没有。

**判断：** 对研究原型可接受；生产化需要把更多规则下沉为代码/策略检查，或至少加审计与告警。

### 3.3 规模与数据保留

- 每个工单一个 DSH Session + 一个目录，资源随并发线性增长；
- SQLite 单文件、单进程锁，不能水平扩展；
- 没有清理机制：trigger/disposition/decision/已结束 Ticket/outbox/版本历史/每条 Source 记录都会无限增长；
- 没有自动备份；文档要求升级前手动备份。

**判断：** 小团队、低并发可用；长期运行需要保留策略、归档/压缩、备份自动化和容量监控。

### 3.4 平台绑定

- 只支持 github.com，不支持 GitHub Enterprise Server；
- 依赖 GitHub 通知语义（编辑 Issue body 加 @ 不会收到，必须新评论）；
- 依赖 `gh` / `lark-cli` 的输出格式；
- 依赖 DSH 的 Session、工具、权限预设、Web 服务和 subprocess；
- 升级 DSH 或插件可能破坏 preset/面板/数据库兼容。

**判断：** 是 DSH 生态内的深度集成，不是通用框架。

### 3.5 模型依赖

- 主动评估的质量取决于模型对规则、意图、设计决策的判断；
- `observe` 模式是必要的安全阀；
- 规则写得太宽会产生噪音，太窄会漏掉工作；
- “设计决策未定就停下”依赖模型遵守 admission 提示词。

**判断：** 需要持续审查 Decision 记录、调整规则和提示词，不能“设好就不管”。

### 3.6 测试与验证的局限

- 1,197 个用例覆盖很广，但本次观察到环境敏感和时序敏感；
- 没有端到端真实 GitHub/Feishu 集成测试（用 mock/假 CLI）；
- 没有性能、压力、安全测试；
- 本次归档没有执行真实部署演练，也没有跑 `pnpm build`。

**判断：** 测试是“研究原型中的优秀水平”，但不是生产验收。

### 3.7 运维复杂度

- 需要独立 DSH profile、独立 GitHub 账号、独立 `gh` 包装器；
- 可选 Feishu 还需要自建应用、bot 权限、独立 `lark-cli` 配置、keychain 共享秘密；
- 需要 tmux、小时检查、状态目录备份；
- 账号/CLI/setup 问题会阻塞整个系统；
- 跨 Source 身份不映射，运营者要自己在提示词里维护“谁是谁”。

**判断：** 对熟悉 DSH 的团队可控；对普通团队门槛不低。

### 3.8 研究原型的自我声明

README 明确说：

- 研究代码，不是官方产品；
- 可能含 bug；
- 编码风格和工程实践可能不一致；
- 为公开发布做过适配，与内部版本/论文不完全一致；
- 论文中一些设计是未来方向，未实现。

**判断：** 不应把仓库描述当作已交付能力清单；引用论文时尤其要区分“设计讨论”和“代码实现”。

### 3.9 上游自身的 open questions

`docs/007-architecture.md` 末尾列出两个未决问题：

1. **信任边界：** 哪些 Trigger 字段可信（Source 的 actor、Thread 成员关系），哪些不可信（正文、引用）；
2. **部署隔离：** 让 agent profile 使用独立、固定版本的 DSH 安装，避免升级其他 DSH 时破坏它。

这两个问题在本归档看来仍然是关键风险，且第 1 个直接关系到提示注入与越权。

## 4. 适用性判断

### 适合

- 一个受信任团队、一个 GitHub 仓库的内部试点；
- 需要一个“能自己开 PR、但只在被请求时行动”的常驻 agent；
- 愿意投入时间配置名单、规则、提示词和小时检查；
- 能接受研究原型的 bug 与运维手工步骤；
- 使用 DSH 作为 agent 运行时。

### 不适合

- 多租户、不可信仓库、高风险生产环境；
- 需要强隔离、细粒度权限、审计合规的场景；
- 大规模并发（数十/数百工单同时跑）；
- 需要 GitHub Enterprise Server 或其他代码托管；
- 希望“开箱即用、无需维护提示词”的团队。

## 5. 对本项目/类似系统的启示

1. **先定义“注意力预算”，再设计通知和交互。** 否则功能越多，噪音越大。
2. **授权分两层：确定性 gate + 结构化模型判断。** 不要让模型直接决定权限。
3. **把外部副作用持久化。** 先存后做、回执去重、按会话保序，是 agent 可靠性的基础。
4. **角色隔离比单 agent 更可维护。** 路由与执行分开，上下文更干净，责任更清晰。
5. **订阅是“上下文路由”，不是授权。** 这个区分能显著减少重复评估，同时不扩大权限。
6. **把文档规则变成测试。** 编号、链接、模块表、JSDoc、模型表面都可以自动检查。
7. **默认 observe。** 主动 agent 的第一版应该是“记录我会做什么”，而不是“直接做”。
8. **研究原型也要写运维手册。** setup、状态码、小时检查、升级/回滚，决定了它能否真的被用起来。

## 6. 最终结论

`dsh-superagent-prototype` 是一个**设计密度很高、工程完成度超出一般研究原型**的系统。它最有价值的部分不是“让 agent 自动写代码”，而是：

- 用领域状态机把“请求 → 授权 → 工单 → 派工 → 交付”讲清楚；
- 用确定性 gate + 结构化评估把权限与语义判断分开；
- 用单写入者、事务、持久化副作用和 outbox 把可靠性做成默认属性；
- 用两个角色的强隔离控制上下文与责任；
- 用提示词版本化、Source 插件协议和文档测试让系统可演进。

它的主要限制也同样清楚：**不是安全隔离架构，不是多租户平台，不是生产级产品**。如果把它当作“受信任单团队、单仓库、DSH 环境下的主动编码 agent 参考实现”，它非常值得研究；如果把它当作可直接托管给不可信用户或高风险仓库的生产系统，则不应采用。
