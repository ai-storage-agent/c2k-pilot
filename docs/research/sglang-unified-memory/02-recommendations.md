# 02 结合我们工作的建议

> 本文把 [01](01-article-analysis.md) 的机制映射到**我们已有的公开工作**：DwarfStar `ds4` 推理引擎（`antirez/ds4`，快照 `b3f50180`）、我们的 Strix Halo TP 分支（`wkljohn/ds4-strix-halo-tp-odinlink`，公开 fork），以及本仓库两个仍在评审中的分析（DS4 SSD 专家 decode 链路 [PR #8](https://github.com/ai-storage-agent/c2k-pilot/pull/8)、AFD 架构与 SGLang 合入状态 [PR #6](https://github.com/ai-storage-agent/c2k-pilot/pull/6)）。
> 原则：**先照搬方法论，再考虑照搬机制；最后才考虑照搬代码。** 所有建议都可独立于 SGLang 实施，且只引用公开来源。

## 0. 一句话

值得学的不是 `--enable-unified-memory` 这个开关，而是它把**"多种生命周期不同的状态共用一个内存池"**做成了**一条可验证的不变量链**：统一的联合需求模型 + 显式页状态 + "逻辑进展驱动决策、各 rank/stage 决策一致" + 分层不变量与 seeded stress harness。我们在多处遇到同构问题（ds4 的 slot/KV/专家缓存、Strix Halo 的统一内存 + SSD 分层），建议按下面优先级采用其**方法论**。

## 1. 最该直接借用的四条设计原则

**P1 —— 把"启动时猜比例"换成"运行时可换手"。**
这是原文收益的根因。收益不在算子更快，而在**消除了一类配置错误**（`--swa-full-tokens-ratio 0.1` 掉 12% 吞吐、`--mamba-full-memory-ratio 0.3` 把并发从 51 压到 24）。对我们最直接的对照物是 ds4 的 `--ssd-streaming-cache-experts`（专家缓存字节预算）与 `--ctx` × `--batched-session`（每 session 独立 KV 状态的预留）。二者都是"启动/配置期一次定死、之后不能互相借用"的量。
**建议：** 先做**可观测性**——为这批量输出"held（精确）/available（估计）"两组数字（照抄 SGLang 的口径区分），再谈动态化。没有 held/available 之分，任何动态化都会先变成统计口径事故。

**P2 —— 需求模型必须只有一份，且所有容量问题都问它。**
原文最硬的一条工程约束是：admission、memory clip、HiCache load-back、PD 预分配、缓存淘汰**共用同一个 demand 函数**（`[文档]`：`ChainAllocator.max_new_tokens_for_memory` 与 `DEMAND_RULES` 的 `CEILING`/`ADMIT`/`LOAD_BACK`/`DECODE_PREALLOC`）。并且**单池空闲字节数只允许出现在日志与指标里**，读取它的决策会被 check mode 标记。
**建议（可立即做）：** 在 ds4 里把"这个请求能不能跑"收敛成一个函数，并加一个 debug 开关，**标记任何在准入/驱逐决策里读取单一池空闲量的代码路径**。这是低成本、高收益的护栏，且不需要先改内存布局。

**P3 —— 逻辑释放立即、物理复用等待；用 ledger 表达"谁还在碰这一页"。**
这是原文对 overlap scheduler 下安全性的全部答案，也是它最可迁移的部分。核心不是加锁，而是：
- 请求表只存**虚拟 id**，搬页只重映射，不改请求表；
- 每个页记录使用类型（forward 写 / host 拷贝 / 网络传输 / 搬移源保护），**"下一个 writer 是什么类型"决定等什么**；
- 源侧保护（vacated / fenced）与目的地状态分开。

ds4 已有同构机制：专家缓存槽位的**淘汰**、`F_RDADVISE`/`madvise` 预读、以及 `ds4_kvstore` 的 disk KV 检查点。但我们的 SSD 分析（[PR #8](https://github.com/ai-storage-agent/c2k-pilot/pull/8)）已指出 decode 路径**不做排序、保持路由顺序**，而 prefill 才按文件偏移排序合并。这正是"在有在途工作时搬/复用"的同一类问题。
**建议：** 给专家槽位与 KV 检查点引入**页/槽状态机**（至少 live / pending / hole 三态，外加"源被读者保护"），并把"何时可复用"从隐式的引用计数，改成 ledger 上可断言的规则。可先只做离线断言与统计，不改变现有调度。

**P4 —— 声明式状态面：新状态组合 = 新声明，不是新 allocator。**
原文明确说"支持新的状态组合意味着写一个新的 declaration，而不是一个新的 allocator"，并让每个层声明"存什么（shape/dtype）+ 活多久（全上下文 / 有界窗口 / 请求级）"。这直接对应我们的现实：ds4 同时有 KV、GQA/稀疏 attention 的 cache、linear-attention（GDN/KDA）的 recurrent state、以及每请求的 convolution/delta-net 状态。我们的公开 fork 文档已经量化过其中一项——GLM-5.3 的 34 个 KDA 层需要每 TP rank **152,633,344 字节（145.56 MiB）**的常驻每序列状态，含三个因果卷积历史与每层 recurrent 矩阵。
**建议：** 把这些状态先整理成一张**声明表**（部件 / 占什么 dtype / 生命周期类别 / 分配单位），即使短期仍各用各的 allocator。这张表本身就是后续统一容量的唯一事实来源，也是评审时最容易发现"某种状态没有生命周期定义"的地方。

## 2. 对 ds4 的具体建议（按优先级）

### 2.1 立即可做（不改架构）

| # | 建议 | 依据 | 验收方式 |
| --- | --- | --- | --- |
| A1 | 把单池空闲量与精确占用分开报告，并给决策路径加"读单池估计"的告警开关 | 原文"单 sub-pool 空闲量只用于日志/指标；check mode 标记读取它的决策" | 开启后跑现有 benchmark，列出所有命中点；确认无准入/淘汰路径命中 |
| A2 | 把准入需求收敛成一个函数（对应 SGLang 的 `ChainAllocator.max_new_tokens_for_memory`） | 原文 admission 与 memory clip 共用一个需求模型 | 单测：同一请求在 clip 与 admission 得到一致结论 |
| A3 | 为专家缓存槽位加最小状态机与离线断言（live / pending / hole） | 原文页四状态 + 两保护；我们的 decode 路径不排序、复用激进 | 不改调度，只在现有路径上断言"复用前该槽的读者已结束" |
| A4 | 记录并公开 `--ctx` 与 `--batched-session` 的联合需求模型（不是各自上限） | 原文"共享字节不把请求足迹简化成 token 数"；ds4 文档已提示"context 放得下一次不等于放得下四次" | 启动时打印联合需求与实际切分，并有一个"若 X 则需 Y"的拒绝理由 |
| A5 | 把 disk KV 检查点的保留边界写成显式规则（类似原文 checkpoint retention floor） | 原文 window 行保留受 checkpoint 驱动，并承认停滞时 admission 只是估计 | 在 `--kv-cache-*` 语义文档中写明"通过 clip 不保证完成"的同类边界 |

### 2.2 中期（需要小范围改动）

- **A6 专家缓存与 KV 的容量换手。** 我们的 SSD 分析已量化：单专家 `9,953,280 B ≈ 9.49 MiB`，全部路由专家 `142.38 GiB`，decode 最坏每 token 读盘约 2.2 GiB，命中率决定速度。原文的"band + 浮空 + 惰性压实"提示了一条不牺牲专家局部性的换手路径：**把"专家缓存"与"KV/上下文"视为两个不同分配几何的 sub-pool**，在负载变化时允许 KV 少留一些 token、专家缓存多留一些槽（或反之），而不是只在启动时定死。注意原文的警告同样适用：**几何不同的两种分配，naive 共享会把空闲容量困在无法使用的缝隙里**——所以必须连同"按各自单位分配"一起做。
- **A7 把"逻辑进展驱动决策"作为并发正确性的判据。** 原文要求所有 allocator 决策只读逻辑状态（计数、已处理 forward、已释放 transfer），**绝不读"这个 event 是否已在本 rank 触发"**，从而 TP rank 决策一致。ds4 的 TP/pipeline 路径正需要这类判据。建议在我们的多卡路径上显式写成规则并加断言。
- **A8 用 seeded stress harness 代替"跑一遍 benchmark"。** 原文的 harness 在真实 allocator + 真实 arena 上跑随机操作序列（overlapped forwards、在途 forward 下释放、window retirement、HiCache load/backup、网络收发、flush、relayout、state copy、hand-out zeroing），并检查 `lost_write`、`unordered_overlap`、`host_read_after_wait`、`rank_divergence`、`cross_dtype_bytes`、`ledger_leak`。我们的 ds4 已有 `make test-ssd-cache` 之类的小测试，但缺少**随机操作序列 + 最小化失败用例**这一层。这是投入产出比最高的一项长期工程。

### 2.3 明确不建议照做的

- **不要为了"统一"而统一。** 原文只替换**混合模型**的池，纯 full-attention 模型直接拒绝——因为此时没有"生命周期不同的多种状态"，统一内存只增加复杂度。同理，若我们某个形态只有一种状态，保留现有专用 allocator 更好。
- **不要在没有 host/device 流抽象的平台上硬上。** 原文因 scheduler 无 device stream 而拒绝 MPS 与 MLX。我们的 Metal/统一内存路径若要做同类排序，必须先有等价的流/事件语义，否则会引入原文明确要避免的竞态。
- **不要把作者自报数字当作我们的预期。** 原文全部收益都是单机、默认比例基线、两次运行平均；且它的目标场景是"流量与启动假设不符"。我们的 Strix Halo 是**统一内存 + SSD 分层**，瓶颈结构不同（带宽与容量而非纯 HBM 容量），必须自测。

## 3. 对 SSD 流式与分层存储路径的建议

我们的 SSD 流式推理（[PR #8](https://github.com/ai-storage-agent/c2k-pilot/pull/8)）与原文的 arena 是同一类问题的两个尺度：**多种访问模式不同的数据，共享一个有限的快层容量**。原文的方法论可迁移为四条通用原则（可独立于 SGLang 实施）：

1. **"访问集合何时确定"必须和"字节何时可复用"一起定义。** 我们的 decode 路径每 token 每层才由 router 选出 top-k 专家，访问集合在运行中确定；而槽位复用是隐式引用计数。原文把"可行性（存在某布局）"与"实现（具体计划，且尽量不动固定页、不惊动在途传输）"分开，提示我们：**合并/淘汰决策应当晚于访问集合确定，但读取可以先开始**。
2. **容量判定要走"联合需求"而非单池水位。** 原文最反直觉的一点是"总需求算对还不够，arena 必须有能供应它的布局"。我们的等价物是：专家缓存够放 ≠ 这次 decode 能跑，还取决于 KV/上下文与 scratch。建议**用一个判定回答"这次请求整体放得下吗"**，而不是逐池比较余量。
3. **搬移只改变"谁能用这些字节"，不改变寻址。** 原文用"虚拟 id + 每池映射"把搬移与请求表解耦。我们的 SSD 路径已有同构思想（专家缓存槽位地址表、slot 指针）；若将来做槽位重排或缓存换手，**逻辑地址稳定、物理位置可重建**应作为前提约束写下来。
4. **把"决策一致性"列为验收项，而不是实现细节。** 原文在 PP 下让各 stage 从同一逻辑计数与各自几何模拟所有 stage，从而无需每次决策交换容量也能一致。我们的 TP/pipeline 路径可直接借用：**用共享逻辑状态 + 各自几何独立得出一致决策**；建议在分布式评审清单里加一条断言：同一逻辑状态与几何下，任意两个 rank/stage 必须得出相同决策。

## 4. 评估方法建议

若要验证我们自己的等价改造，建议照抄原文的**对照设计**而不是照抄它的数字：

1. **基线必须是"我们自己的默认配置"**，而不是 SGLang 的比例。原文的对照是"统一内存 vs 分离池默认比例"，我们应做"动态换手 vs ds4 当前默认"。
2. **至少两个反例负载**：一个长上下文（压力偏向 KV/上下文）、一个多短并发（压力偏向专家缓存/状态槽）。原文正是用这两类负载证明"搁浅发生在相反方向"。
3. **报告口径要与原文对齐**：吞吐（tok/s）、并发请求数、TTFT、retraction 次数，并**明确标注是否限制了并发**——原文特意指出 `ratio 0.3` 的"0 retraction"是压低并发的假象。我们的等价陷阱是"少读盘"其实是"少服务请求"。
4. **必须报告 held（精确）与 available（估计）两组数字**，并说明哪些是估计量。
5. **单次运行不等于结论。** 原文两次运行平均、无方差；我们若做对比至少交替顺序重复，并记录 commit、量化、上下文、采样参数（我们 `docs/PERFORMANCE.md` 已有这条纪律）。

## 5. 一句话收尾

SGLang 这篇博客证明了一件事：**当一个系统的多种状态生命周期不同步时，"统一容量 + 显式状态 + 一致性决策 + 可验证的页安全"能同时消除一类配置错误和一类并发缺陷。** 我们不缺同构的问题（KV、recurrent state、专家缓存、SSD 分层），缺的是把它收敛成同一条不变量链。建议从 §2.1 的 A1–A5 开始，其中 A2（单一需求模型）与 A3（槽状态机断言）几乎不需要改动现有调度，却能立刻提高可评审性。
