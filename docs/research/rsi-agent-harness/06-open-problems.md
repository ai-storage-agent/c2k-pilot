# 06 · 开放问题与研究空白

> 本页回答"参考架构里哪些部分还没有可靠答案"。每一项都标注证据强度与它对架构的影响。
> 与 [04](04-reference-architecture.md) 的分层对应；引用见 [references.md](references.md)。

## 0. 证据强度标注约定

| 标注 | 含义 |
| --- | --- |
| **【理论】** | 形式化结果，不依赖实验设定 |
| **【实证·多源】** | 多个独立工作的一致发现 |
| **【实证·单源】** | 单一工作的发现，尚无独立复现 |
| **【自报】** | 作者自报数字，未独立复现 |
| **【推测】** | 本调研基于证据的推断，不是论文结论 |

## 1. 验收门的可靠性（最高优先级）

### 问题

**在什么条件下，自动验收门可以可信地接受一次自我修改？**

### 已知

- **【理论】** 全一般设定下，不存在同时保证可靠性与非保守性的终止性门（[2610.21646](references.md#ref-2610-21646)）。
- **【理论】** 有界评估 + 有限提案预算构成一个可判定区间，穷举模拟可行。
- **【实证·多源】** 实践中门会系统性失效：遮罩侵蚀、验证者退化、基准过拟合、代理信号失效。
- **【实证·单源】** 移除锚点守护后评分器坍缩为恒通过，但下游训练效果不变（[2610.11464](references.md#ref-2610-11464)）。

### 空白

1. **"有界区间"的边界在哪里？** 任务数与提案预算需要多小才能让穷举模拟可行，同时不使改进停滞？这是一个可测量的工程问题，但尚无系统研究。
2. **门的失效能否被提前检测？** 遮罩侵蚀在删除时不可见，只在复用更弱模型时暴露。是否存在可在删除时刻计算的"冗余深度"指标并设下限？
3. **多信号委员会的最优构成是什么？** 主指标、回归、约束、验证器自审计、成本——各自的权重与阈值如何校准？目前是手工设计。
4. **验证器的自审计能否自动化？** 锚定参考集需要人工编写；能否从历史评估中自动构造？

### 对架构的影响

参考架构把门设计为"必要不充分"条件并保留人工否决（[04 §8.1](04-reference-architecture.md)）。若问题 2/3 有进展，可安全放开的自修改层级会显著提高。

## 2. 改进是否真实（证据质量）

### 问题

**如何区分"分数上升"与"能力提升"？**

### 已知

- **【实证·多源】** 代理信号不足以判定能力形成：制品累积 + 行为改变 + 指标上升三者同时存在，能力仍可能未形成（[2611.04952](references.md#ref-2611-04952) 的三个反例）。
- **【实证·单源】** 重跑率极低：仅 22% 的 RSI 研究审计 ≥2 次完整循环重跑；26 项声称"改进过程更好"的研究中仅 4 项在相同起点、匹配预算下比较（[2610.27610](references.md#ref-2610-27610)）。
- **【实证·单源】** 失败衍生经验能修复已失败任务，但很少泛化到未见过任务（[2610.22984](references.md#ref-2610-22984)）。
- **【实证·单源】** 基准增益与人类偏好增益无清晰关联（RSI Arena）；某些 agent 倾向更长回答，一个模型在 StrongREJECT 上有害合规上升。

### 空白

1. **"能力形成"如何操作化？** [2611.04952](references.md#ref-2611-04952) 提出五个顺序依赖属性并区分 state/game/lineage 三层诊断，但目前只是一个受控环境（五子棋）中的存在性证明。
2. **修复率与泛化率的最小报告集是什么？** 需要一组被广泛接受的指标，让不同工作报告可比。
3. **负结果如何被系统记录？** 被拒绝的候选及其理由是诊断下一轮改进的主要输入，但目前几乎没有工作公开这部分数据。
4. **如何检测"合法性增益"这类伪提升？** 需要自动构造反事实对照。

### 对架构的影响

参考架构强制三层证据（更新级 / 后继级 / 元改进级）与 L0–L3 成熟度标注（[04 §7.1](04-reference-architecture.md)）。这些目前是**最佳实践建议**，不是被验证的方法。

## 3. 稳定性-可塑性权衡

### 问题

**自演化 agent 能否在不遗忘的情况下持续适应？**

### 已知

- **【实证·单源】** 在四个漂移任务流上，ReasoningBank、GEPA、Meta-Harness 的自演化在多数流上提升总体表现，但**更高的可塑性持续以稳定性为代价**：全局编辑共享 prompt/workspace 干扰未见过任务、覆盖旧知识；相似度检索局部化更新但仍会检索到过时经验（[2610.25858](references.md#ref-2610-25858)）。
- **【实证·单源】** 技能-策略共同演化陷阱：策略能力绑定于共同训练的 skill bank，部署后技能漂移使策略脆弱；敏感性随共同演化训练推进而增长（[2610.20845](references.md#ref-2610-20845)）。
- **【实证·多源】** 记忆的陈旧性是已知失败模式；[2605.06716](references.md#ref-2605-06716) 的 Storage → Reflection → Experience 三阶段是对此的回应。

### 空白

1. **局部化更新的最优粒度是什么？** 按任务域、按技能、按提示词段落？尚无系统对比。
2. **遗忘机制如何设计？** 显式剪枝需要判断"这个制品已失效"，但失效判据本身可能是错的。
3. **稳定性与可塑性能否被同时量化？** [2610.20845](references.md#ref-2610-20845) 的 CODA 提出一致性率与抗腐蚀率两个指标；能否推广为通用报告标准？

### 对架构的影响

参考架构要求更新局部化并显式剪枝（[04 §4.2](04-reference-architecture.md)、[04 §11](04-reference-architecture.md)），但没有给出粒度选择的方法。这是最大的实现不确定性之一。

## 4. 验证器的独立选择

### 问题

**当验证器与被改进对象共同演化时，如何保证验证器没有退化？**

### 已知

- **【实证·单源】** 按与 agent 分数无关的标准（锚定参考集 + 无标注输出上的一致性）选择验证器是可行的；MBPP+ 上比手工种子组合高 +0.21 的 held-out 一致性（[2610.11464](references.md#ref-2610-11464)）。
- **【实证·单源】** **下游任务分数不能证明自演化验证器有效**——坍缩的恒通过评分器训练技能一样好。
- **【实证·单源】** 需要外层 judge 才能抓住被游戏化的评分。

### 空白

1. **锚定参考集从何而来？** 目前是手工编写（十项锚定集）。自动构造方法与最小规模未知。
2. **验证器退化的早期信号是什么？** 除"恒通过"外的退化形态未被系统枚举。
3. **多验证器投票是否优于单一验证器？** 共享盲点问题是否因此缓解？

### 对架构的影响

参考架构强制 L4 与 L3 的单向依赖，并要求验证器自审计（[04 §8.4](04-reference-architecture.md)）。锚定参考集的人工成本是实际部署的门槛。

## 5. 约束的保持与冗余深度

### 问题

**如何度量并防止安全约束的静默流失？**

### 已知

- **【实证·单源】** 重叠守护下删除单个不可见；门只看任务成功，冗余深度无声流失。相同成本下，40 任务批量丢掉了全部六个守护，20 任务批量一个都没丢（[2610.38392](references.md#ref-2610-38392)）。
- **【实证·单源】** 统计显著性检验能挡住"靠运气通过"的删除，挡不住"真正提升任务成功"的删除。
- **【实证·单源】** 大危害审计能防止暴露，但不能防止深度流失；流失在复用更弱模型时转化为危害。GEPA 保留了每一条安全规则原文，但其三个最终 harness 中有两个在更弱模型下误用凭据。

### 空白

1. **冗余深度如何形式化定义与计算？** 需要能处理"两个守护是否真的独立"的问题。
2. **守护独立性如何测试？** 需要为每个约束构造能单独触发它的场景。
3. **弱模型重放应是常规流程吗？** 它暴露被强模型掩盖的风险，但增加成本。

### 对架构的影响

参考架构把冗余深度设为一等指标并设不可下降下限（[04 §8.2](04-reference-architecture.md)）。定义与计算方法是实现时的首要任务。

## 6. RI（修订改进机制自身）的可验证性

### 问题

**当系统修订 `U` 时，此前的验证结果是否仍有意义？如何重新验证？**

### 已知

- **【理论】** 修订 `U` 会改变未来偏置更新的方式，使此前验证可能失效（[2610.35193](references.md#ref-2610-35193)）。
- **【实证·单源】** 匹配起点 + 匹配预算的机制对比是可操作的，但仅 4 项研究做到（[2610.27610](references.md#ref-2610-27610)）。
- **【实证·单源】** [2610.38266](references.md#ref-2610-38266) 的 L0–L3 标尺把"经验证的改进器增益"（L3）与"继承的过程修订"（L2）分开，并提出共享数据与交互式对比方法。

### 空白

1. **元改进级证据的最小标准是什么？** 需要几次重跑、多大预算、什么起点对齐？
2. **元不变量内核应包含什么？** 安全约束、权限边界、审计要求、终止条件——但边界在哪里？内核越大，RI 越安全也越受限。
3. **RI 的收益是否已被证实？** 目前几乎没有工作展示"修订 `U` 后改进过程本身变强"的严格证据。这是一个**可能尚不存在的实证基础**。

### 对架构的影响

参考架构把 RI 设为默认关闭、逐级启用的最高成熟度阶段（[04 §6.5](04-reference-architecture.md)、[04 §10](04-reference-architecture.md)）。**鉴于空白 3，这一设计是谨慎而非已验证的：当前不应该在任何生产系统中默认启用 RI。**

## 7. Harness 泛化

### 问题

**演化出的 harness 是局部最优补丁，还是可复用能力？**

### 已知

- **【实证·单源】** ADAS 报告 Meta Agent Search 发现的 agent 跨域、跨模型迁移后仍优于手写 agent（[2408.08435](references.md#ref-2408-08435)）。
- **【实证·单源】** 但 [2610.30042](references.md#ref-2610-30042) 指出规划任务中"改进 agent 的能力"与"被改进的能力"不重合，开放式自修改会大量浪费评估预算——即迁移不一定发生。
- **【实证·多源】** 多数 harness 演化工作只在有限基准集上验证。

### 空白

1. **迁移的度量标准是什么？** 需要跨域、跨模型的固定评测协议。
2. **什么类型的 harness 改进可迁移？** 工具改进 vs 提示词改进 vs 控制流改进，可能差异很大。
3. **`B`/`U` 层改进是否比 `h` 层改进更可迁移？** 理论上有理由（更抽象），但无实证。

### 对架构的影响

参考架构把 harness 泛化列为开放挑战（[03 §8](03-harness-anatomy.md)），不假设演化结果可迁移。

## 8. 成本与预算的度量

### 问题

**如何让改进循环不收敛到最昂贵的选择？**

### 已知

- **【实证·单源】** 评估预算分配有明确的最优结构：搜索期稀疏 + 最终定向确认，多数设定下平均表现高于全量评测而评估量约为一半（[2610.37276](references.md#ref-2610-37276)）。
- **【实证·单源】** 单基准 $500 平台服务预算下可运行五基准联合改进（[2610.10310](references.md#ref-2610-10310)）。
- **【实证·多源】** 报告成本是评估卫生的必要部分（[2407.01502](references.md#ref-2407-01502) 批评只看准确率导致 SOTA agent 不必要地复杂与昂贵）。

### 空白

1. **成本应如何进入验收门？** 作为硬约束、软惩罚，还是独立维度？
2. **不同成本类型（token、工具调用、墙钟、资金）如何折算？**
3. **长期运行的总成本模型是什么？** 改进循环的边际收益何时低于边际成本？

### 对架构的影响

参考架构把成本列为验收门的独立信号并要求核算（[04 §6.3](04-reference-architecture.md)、[05 §3.4](05-implementation-blueprint.md)）。

## 9. 训练时与推理时的分工

### 问题

**harness 应该拥有多少训练能力？**

### 已知

- **【实证·单源】** 零数据自玩路线在 2025 年取得实质进展，但都依赖可执行验证器（代码执行、形式验证、可判定答案）。
- **【实证·单源】** [2504.13837](references.md#ref-2504-13837) 对"RL 是否真的扩展了基础模型之外的推理能力"提出质疑：大 k 下基础模型 pass@k 高于 RLVR 训练版本；RLVR 主要锐化基础分布。
- **【实证·多源】** 模型坍塌是自生成数据循环的已知风险；把合成数据与真实数据**累积**（而非替换）可避免坍塌。

### 空白

1. **harness 与训练栈的接口契约是什么？** 需要标准化的轨迹格式、验证器接口、检查点晋级流程。
2. **检查点作为制品进入 L2 后，走同一套验收流程是否合适？** 权重变更的验证要求与 prompt 变更显然不同。
3. **"能力提升"与"分布内拟合"如何在 harness 层被区分？** 需要设计能区分二者的评估。

### 对架构的影响

参考架构为训练时 RSI 定义了三类接口，并明确边界（[05 §8](05-implementation-blueprint.md)）。接口细节需要标准化工作。

## 10. 领域特定约束

### 问题

**参考架构在安全关键领域需要什么额外机制？**

### 已知

- **【实证·单源】** [2606.20683](references.md#ref-2606-20683) 的领域画像：软件工程验证主导、web/GUI grounding 主导、科学发现综合主导、医疗辅助安全主导、具身控制主导。
- **【实证·单源】** 开放环境（web、桌面）的治理比编码场景更核心，因为动作可能部分不可逆且缺少干净 oracle。

### 空白

1. **不可逆动作的审批层级如何系统推导？** [2610.19591](references.md#ref-2610-19591) 用效果可逆性推导工具审查层级，但在通用领域如何枚举"效果可退多远"？
2. **多利益相关者的可信度如何定义？** [2610.35193](references.md#ref-2610-35193) 把它列为开放问题。
3. **监管与合规要求如何映射到 L5 的审计记录？** 参考架构的审计字段是技术驱动而非合规驱动。

### 对架构的影响

参考架构的安全机制是领域无关的基线；安全关键领域需要在其上增加领域特定的审批与验证。

## 11. 未决问题汇总与优先级

按"对架构的影响 × 可行性"排序：

| 优先级 | 问题 | 为什么优先 | 可行性 |
| --- | --- | --- | --- |
| **P0** | 冗余深度的定义与计算（§5） | 决定了约束保持能否被机械检查；是"安全地放开自修改"的前提 | 高（可在现有评估框架内实现） |
| **P0** | 修复率 vs 泛化率的报告标准（§2） | 决定了"改进是真的吗"这一核心问题 | 高（主要是协议工作） |
| **P1** | 验证器锚定集的自动构造（§4） | 降低验证器独立选择的部署门槛 | 中 |
| **P1** | 局部化更新的粒度选择（§3） | 直接决定稳定性-可塑性权衡的实测结果 | 中 |
| **P1** | 成本进入验收门的方式（§8） | 防止改进循环收敛到最贵方案 | 高 |
| **P2** | 门的多信号委员会校准（§1） | 提高可安全放开的层级 | 中（需要大量实验） |
| **P2** | harness 泛化的度量协议（§7） | 判断演化产出是否可复用 | 中 |
| **P2** | 训练接口标准化（§9） | 决定训练时 RSI 能否低成本接入 | 中 |
| **P3** | 元改进级证据标准（§6） | 为 RI 提供实证基础；但 RI 本身尚未被证明有收益 | 低（缺乏实验对象） |

## 12. 明确**不应**做的事

根据现有证据，以下做法在当前证据水平下不应采用：

| 做法 | 原因 |
| --- | --- |
| 在生产系统中默认启用 RI | 元改进级证据几乎不存在；且修订 `U` 会使先前验证失效 |
| 用单一标量分数作为验收门 | 已被多源实证证明会被游戏化 |
| 用下游任务分数证明验证器有效 | [2610.11464](references.md#ref-2610-11464) 的坍缩反例 |
| 把"分数上升"当作"能力提升" | 代理信号失效的多个反例 |
| 用全局重写优化共享 prompt | 稳定性-可塑性权衡的实证代价 |
| 删除旧轨迹以节省空间 | 与"累积而非替换可避免坍塌"的建议相反 |
| 只在 select split 上评估就接受 | 基准过拟合的已知机制 |
| 报告单次运行的增益 | 重跑率仅 22% 的领域现状正是问题所在 |

## 13. 小结

参考架构中**最可靠**的部分是：六职责分解（有综述与经验证据支持）、S1–S4/RI 的形式化（有严格定义）、门的不可能性（有理论证明）、以及若干具体失败模式（有多源实证）。

**最不可靠**的部分是：冗余深度的计算、验证器独立选择的具体方法、局部化的粒度、以及 RI 的收益论证。这些是后续研究的最高价值目标，也是把参考架构从"设计蓝图"推进到"可部署系统"的关键路径。
