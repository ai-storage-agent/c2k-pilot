# 03 · Harness 解剖：六职责与执行信号

> 本页回答"harness 到底是什么、它如何决定 agent 能力、以及它如何为自我改进提供信号"。
> 主要依据 [2606.20683](references.md#ref-2606-20683) 的六职责分解，并用 SWE-agent、DGM、[2610.35193](references.md#ref-2610-35193) 等独立工作交叉验证。

## 1. 从"模型"到"模型 × harness"

### 1.1 功能视角 vs 实现视角

文献中常混淆两个抽象层次：

- **功能层（function view）：** agent 是一个目标导向的闭环系统——感知环境、维护状态、推理决策、执行动作、从反馈适应。这定义 agent **必须做什么**，与实现无关。
- **实现层（implementation view）：** LLM-based agent **不是**基础模型本身，而是"基础模型 + 执行 harness"的耦合系统。模型提供语言理解、推理、规划、动作提议；harness 提供暴露观测、构造上下文、执行动作、持久化状态、验证与恢复的运行时机制。

形式化（[2606.20683](references.md#ref-2606-20683) 式 1）：

```text
A_LLM = ⟨M, H⟩ = ⟨M, I_obs, C, L, I_act, S, V⟩
```

其中 `M` 是模型层（单模型或多模型集合），`H` 是执行 harness，展开为六项运行时职责。

**这个分解的意义：** 它把"agent 能力"从模型属性变成**模型- harness 配对的属性**。同一模型配不同 harness，表现可以差一倍以上（见 §5 证据）。

### 1.2 为什么这决定 RSI 的可能性

如果能力只来自模型，那么自我改进只能通过训练权重实现——成本高、周期长、且受算力约束。
如果能力来自模型 × harness，那么改进空间大幅扩张：

| 可改进对象 | 是否需要梯度 | 典型反馈周期 | 风险 |
| --- | --- | --- | --- |
| 权重 | 是 | 小时–天 | 高（不可逆、难归因） |
| 提示词 | 否 | 秒–分 | 低 |
| 记忆组织 | 否 | 秒–分 | 低-中 |
| 技能库 | 否 | 分–小时 | 中 |
| 工具/动作接口 | 否 | 分–小时 | 中（安全边界） |
| 工作流/控制流 | 否 | 分–小时 | 中-高 |
| harness 源码 | 否 | 小时 | 高 |

**这正是 RSI 研究在 2024–2026 年集中在 harness 层的原因：** 它提供了"无梯度、可验证、可回滚"的改进通道。

DGM 的自述很直接：它自动改进出更好的**代码编辑工具**、**长上下文窗口管理**、**同行评审机制**——全部是 harness 层制品，而非模型权重。A Self-Improving Coding Agent 同样报告"带基础编码工具的 agent 系统自主编辑自身"。

## 2. 六项运行时职责

### 2.1 观测接口 `I_obs`

**做什么：** 决定哪些环境信号暴露给模型、以什么形式渲染。把外部状态（终端输出、文件 diff、截图、DOM、API 响应、事件流、日志）转换为模型调用可消费的观测。

**设计问题：** 哪些状态相关、在什么抽象层次表示、何时刷新。

**为什么重要：** 很多长周期失败不是推理失败，而是**可读性失败**——需要的状态缺失、被噪声淹没、已过期、或表示的层次不支持下一步决策。

| 代表系统 | 证据 |
| --- | --- |
| SWE-agent | 重设计 agent-computer interface 后，固定基础模型下 SWE-bench 大幅提升 |
| WebArena / OSWorld | web 与桌面场景的成功取决于能否把视觉与结构复杂的界面状态转换成模型可用的形式 |

**主导权衡：** 丰富度 vs 可处理性。丰富观测改善 grounding，但增加上下文成本与干扰；压缩观测易于处理，但可能丢弃任务关键证据。

**开放问题：** 在部分可观测、多模态、长轨迹条件下，如何设计既忠实又决策可用的观测接口。

**RSI 含义：** 观测构造器是可修改面，也是**作弊面**。修改观测使答案可见，会在指标上表现为巨大提升。因此观测层变更应被归类为高风险，需要更强的验证。

### 2.2 上下文管理器 `C`

**做什么：** 决定哪些可用信息进入当前模型调用、以什么形式。在选择、压缩、排序、刷新观测、工具输出、检索证据、记忆记录、摘要、指令、任务制品。

**形式化（[2606.20683](references.md#ref-2606-20683) 式 3–4）：**

```text
C = A(c_1, c_2, ..., c_n)
F* = argmax_F E_{τ~T}[ Reward( P_θ(Y | C_F(τ)), Y*_τ ) ]
```

`A` 是高层组装函数；工程问题从"优化提示词措辞"变为"优化检索、选择、压缩、格式化、刷新的函数集合 `F`"。

**关键区分：** 不是"长提示 vs 短提示"，而是**单体上下文 vs 被管理的上下文**。MemGPT 把活动上下文与更大的外部记忆分离；工业 harness 越来越多地把任务状态外化为显式制品并有选择地重新浮现，而不是依赖不断增长的对话轨迹。

**主导权衡：** 忠实度 vs 可管理性。原始历史保留细节但扩展性差；摘要与检索上下文更便宜但可能遗漏或扭曲重要状态。

**RSI 含义：** 上下文策略是最高频、最低风险的自我修改目标。但 [2610.25858](references.md#ref-2610-25858) 的稳定性-可塑性权衡表明：**全局重写共享 prompt 会干扰未见过任务并覆盖旧知识**。因此修改应优先局部化。

**跨层耦合：** 上下文压缩会削弱下游验证能力——压缩率提升必须与验证召回一起评估。

### 2.3 控制循环 `L`

**做什么：** 跨步骤、工具、可能的手交组织执行。决定是简单 perceive-act、ReAct 式循环、plan-execute-verify 例程，还是层级/多 agent 工作流。

**设计问题：** 控制权如何在模型与运行时之间划分、计划何时创建或修订、何时引入委派、协调是串行还是并行、何时停止。

**代表系统：** 轻量迭代循环；显式 planner-executor-verifier 分解；多 agent 协调。

**RSI 含义：** 工作流图与编排拓扑是明确的演化对象。ADAS 的 Meta Agent Search 让元 agent 在代码空间编程出更好的 agent；AFlow 自动化 agentic workflow 生成；[2606.20683](references.md#ref-2606-20683) 指出 NLAH 把 harness 逻辑形式化为可编辑、可移植的自然语言制品，Meta-Harness 把 harness 配置当作可优化搜索空间。

**主导权衡：** 适应性 vs 稳定性。更自由的循环能响应意外状态，但更易漂移、重复失败、协调开销大；更强编排提升可靠性，但可能降低效率或过度约束探索。

### 2.4 动作接口 `I_act`

**做什么：** 把模型输出映射为可执行操作。定义 agent **能做什么**、动作如何指定、适用哪些权限、结果如何作为后续观测返回。

**设计空间：**

| 维度 | 范围 |
| --- | --- |
| 粒度 | 低层环境操作 ↔ 高层 API |
| 规格 | 自由形式命令 ↔ 结构化 schema |
| 路由与互操作 | 本地工具 ↔ 协议化生态（MCP 等） |
| 治理 | 权限、副作用控制、调用约束 |

**为什么重要：** [2606.20683](references.md#ref-2606-20683) 引用诊断工作指出，agent 失败常常不是"工具缺失"，而是工具被**错误选择、错误调用、或没有被正确整合进执行轨迹**。SWE-agent 是观测-动作协同设计的经典案例：重设计 ACI 同时改变模型看到什么与如何行动。

**主导权衡：** 灵活性 vs 可控性。低层工具通用但难以稳健使用；高层工具提升可靠性但可能过度收窄行为。

**RSI 含义：** 这是**安全边界所在层**。DGM 自动演化出的"更好的代码编辑工具"属于此层；[2610.19591](references.md#ref-2610-19591) 用"效果可逆性"直接推导工具的审查层级。新增或扩大动作空间必须与权限控制、沙箱、回滚强度同步提升。

### 2.5 状态与制品存储 `S`

**做什么：** 跨步骤、跨会话、跨子任务持久化执行状态。存储任务进度、轨迹、计划、检查点、diff、生成文件、记忆记录与其他可复用制品。

**设计空间：** 存储粒度、持久化范围、存储形式、更新策略。

**关键洞察（[2606.20683](references.md#ref-2606-20683)）：** 长周期 agent 常常不是因为"没有存状态"而失败，而是因为**存了错误的状态**、**需要的状态取不回来**、或**陈旧状态被当作当前事实**。实际挑战不是存更多，而是决定什么值得持久化、什么该压缩、什么该丢弃。

**代表策略：** 会话级历史与检查点；显式长期记忆（MemGPT）；以制品为中心的 harness 用日志、diff、检查点与可检查的运行时对象跟踪状态。

**主导权衡：** 完备性 vs 可用性。更丰富的状态改善连续性、可审计性与交接，但增加检索负担、噪声与陈旧记忆风险。

**RSI 含义：** 记忆与技能库从"轨迹保存"演进到"轨迹抽象/经验"。RSI 要求状态**可失效、可溯源、可回滚**——这是普通 agent 状态存储通常不具备的。

### 2.6 验证与治理 `V`

**做什么：** 在运行时检查、约束、修复执行。验证包括测试、断言、验证器模型、judge 信号等估计执行是否正确推进的机制；治理包括审批门、沙箱、预算控制、回滚、重试、升级、安全终止。

**这两个角色紧密耦合：** 验证产生关于运行的证据，治理决定 harness 被允许或要求对这些证据做什么。

**核心论断：** 可靠 agent 不仅依赖强推理与丰富工具，还依赖**检查与约束是否被机械强制，而不是完全交给提示词服从**。

**代表系统：** 编码 agent 中，测试、linter、断言提供较强验证信号，回滚与沙箱执行约束副作用；web/桌面等开放环境中治理更核心，因为动作可能部分不可逆且常有干净的 oracle。

**主导权衡：** 自主性 vs 稳健性。更松的约束允许更广探索但增加有害动作与不可恢复漂移的风险；更紧的治理提升安全与可恢复性但可能拖慢执行或阻断有用行为。

**RSI 含义：** 这是与普通 agent 差别最大的一层。普通 agent 的验证服务任务完成；RSI 的验证还要服务"是否接受这次自我修改"。且验证器本身会成为演化对象，因此需要"验证验证器"的独立机制。

## 3. 跨层耦合

六项职责**分析上可分离，运行上不独立**：

```text
I_obs ──紧耦合── C          更丰富的观测改善 grounding，但增加选择/压缩/格式化的成本
I_act ──紧耦合── V          更强的动作能力需要更强的权限控制、沙箱、回滚、审计
S ──反馈──→ C 与 V          持久化的计划/日志/检查点既决定能重新浮现什么，
                            也决定判断进展可用的证据
```

**因此 harness 设计是耦合系统问题，不是六个模块的独立优化。** 改善一层可以把风险转移到别处：

- 更强的压缩降低成本，但削弱下游验证；
- 更丰富的动作改善任务覆盖，但增加治理压力；
- 更持久的状态改善连续性，但引入陈旧或冲突证据。

**这一耦合性使"任务结构"成为 harness 设计的一部分。** 不同领域、视界、oracle 强度、自主性要求对六项职责施加不同的压力剖面。

## 4. 任务压力剖面 → harness 配置

[2606.20683](references.md#ref-2606-20683) 用三个维度刻画任务压力：**任务视界、环境类型、自主性水平**。

### 4.1 任务复杂度与主要瓶颈

| 层级 | 描述 | 例子 | 主要瓶颈 |
| --- | --- | --- | --- |
| **L1** | 单步 | 搜索、翻译、计算 | 上下文管理；验证与治理 |
| **L2** | 多步 | 填表、代码生成 | 动作接口；状态存储；验证与治理 |
| **L3** | 长周期 | 仓库级编码、研究 | 上下文管理；状态存储；控制循环 |
| **L4** | 开放式 | 监控、自动探索 | 验证与治理；控制循环 |

**最关键的跃迁通常是 L2 → L3**：单步与短多步任务可用局部推理、轻量动作访问与局部检查处理；长周期任务对上下文管理、状态存储、控制循环施加持续压力，因为计划、中间制品、失败尝试与部分结果必须活过一个提示窗口。L4 还需要预算控制、停止条件与升级策略，瓶颈转向显式的验证与治理。

### 4.2 环境类型

| 环境 | 压力集中处 |
| --- | --- |
| 终端与仓库 | 动作接口、观测接口、验证与治理（命令/diff/日志/测试可被包装为结构化动作、观测与验证信号） |
| 浏览器与桌面 | 观测构造、动作抽象、权限边界（视觉/DOM grounding、会话状态、持久副作用） |
| 知识环境（检索、文献、数据库） | 上下文管理、状态存储（证据质量、溯源、综合） |
| 物理环境 | 控制循环、验证与治理（实时约束与不可逆性） |
| 社交环境 | 更丰富的观测设计、保守升级（规范、协商、策略性回应） |

### 4.3 领域 bottleneck 画像

| 领域 | 画像 | 说明 |
| --- | --- | --- |
| 软件工程 | **验证主导** | build、单测、linter、执行反馈提供强信号 |
| web / GUI | **grounding 主导** | 界面状态转换是瓶颈 |
| 科学发现 | **综合主导** | 证据质量与假设生成 |
| 医疗辅助 | **安全主导** | 高风险、不可逆 |
| 具身 agent | **控制主导** | 实时性与物理约束 |

### 4.4 自主性水平

自主性是 harness 需求的**乘数**：

| 水平 | 治理方式 |
| --- | --- |
| Human-in-the-loop | 高风险决策走审批门 |
| 半自主 | 常规动作委派，不确定性升高时升级 |
| 全自主 | 必须把更多负担吸收进 harness：验证、回滚、日志、fail-safe 终止 |

越独立行动的系统，观测接口与验证/治理越从可选的护栏变成**主要瓶颈**。

**对 RSI 的直接含义：** RSI 是"全自主"的极端形式——它连"是否修改自己"都要自主决定。因此它对验证与治理的要求远高于普通 L4 任务。

## 5. Harness 是性能杠杆：经验证据

| 证据 | 内容 |
| --- | --- |
| SWE-agent (2405.15793) | 固定基础模型下，仅重设计 agent-computer interface 就把 SWE-bench pass@1 提到 12.5%、HumanEvalFix 到 87.7%，远超非交互式 LM 的先前 SOTA |
| DGM (2505.22954) | 自修改 harness 使 SWE-bench 20.0% → 50.0%，Polyglot 14.2% → 30.7%；自动改进出更好的编辑工具、长上下文管理、同行评审机制 |
| A Self-Improving Coding Agent (2504.15228) | agent 系统自主编辑自身，SWE-bench Verified 随机子集 17% → 53% |
| HarnessMM (2610.32813) | 对 harness 配置做 RSI：DeepSeek Harness 上成功率 71.43% → 85.71%，tokens/task 96.28k → 11.62k（降 87.93%） |
| RSIGym (2610.10310) | Joint 轨道同时优化数据与执行 harness：SWE-bench Verified 17.67% → 50.33%，AIME 31.67% → 97.78%，RSI-Index 0.4809（$500/基准预算） |

这些数字都是**作者自报**，且来自不同基准与设定，不能直接横向比较。它们的共同含义是：**harness 层的改进空间与模型层同量级**，而成本低得多。

## 6. Harness 如何为自我改进提供信号

自修改需要"哪里不好"与"改得对不对"两类信号。harness 六职责正好提供：

| 信号类型 | 来源职责 | 具体内容 | 用于 |
| --- | --- | --- | --- |
| **失败定位** | `V` | 测试失败、断言违例、验证器诊断 | S1 诊断 |
| **执行证据** | `I_obs` + `S` | 轨迹、diff、日志、检查点 | S1 诊断、S2 提案上下文 |
| **成本信号** | `L` + `S` | token、工具调用、墙钟 | S3 验收、预算分配 |
| **任务结果** | `V` | 通过/失败、分数 | S3 验收 |
| **上下文使用** | `C` | 哪些信息被读、被忽略 | S1 诊断（可读性失败） |
| **动作可靠性** | `I_act` | 工具选择/调用成功率 | S2 提案（工具改进） |

**关键要求：轨迹必须充分结构化。** 自由文本日志不足以支持 S1 的结构化诊断；参考架构要求轨迹包含状态、动作、观测、结果与成本（见 [05 §8](05-implementation-blueprint.md)）。

## 7. 四阶段工程范式演进

[2606.20683](references.md#ref-2606-20683) 用四阶段刻画瓶颈迁移。这不是严格的时间划分——四个阶段在今天的系统中并存。

| 阶段 | 优化对象 | 解决的问题 | 遗留问题 |
| --- | --- | --- | --- |
| **P1 提示工程** | 单轮指令 | 表达与能力激发 | 无法提供缺失知识、管理动态状态、验证外部动作 |
| **P2 工作流与上下文工程** | 多步执行周围的信息生命周期 | 信息缺失与状态变化 | **前馈**：没有结构性机制检测漂移、验证中间结果、从错误恢复 |
| **P3 Harness 工程** | 整个运行时基础设施 | 闭环反馈：漂移预防、稳定执行、错误恢复、沙箱、检查点、子 agent 协调 | 把多少行为放在模型里、多少留在运行时 |
| **P4 Agent-native 训练与共同演化** | 模型与 harness 的联合 | 内化（规划/工具/验证/恢复被训练进参数）+ 共同演化（模型、harness、改进循环从执行轨迹更新） | 如何让全栈安全地随时间改进 |

**P3 内部的进一步迁移：** 早期 harness 用固定基础模型 + 手工/搜索出的运行时策略；近期转向**多模型 harness**（运行时路由、委派、组合异构模型），并且 **harness 本身变成可学习的**——harness 模块、编排逻辑、运行时策略可作为一等制品被编辑、搜索、优化。

**这正是 RSI 的入口。** 当 harness 变成可编辑制品时，"谁/什么来编辑它"就成为核心问题。

## 8. 开放挑战

[2606.20683](references.md#ref-2606-20683) 列出的四个方向，对 RSI harness 尤其相关：

| 挑战 | 内容 | 与 RSI 的关系 |
| --- | --- | --- |
| **价值感知的评估** | 从"分数"转向"价值"——成功率、成本、延迟、安全、泛化的联合目标 | RSI 的验收门必须是多信号委员会，不能是单一分数 |
| **学习去验证、恢复、适应** | 验证与恢复本身成为训练目标 | 与验证器共同演化问题直接相关 |
| **Harness 泛化 vs 专用** | 演化出的 harness 能否跨域迁移 | 决定 RSI 产出是"局部最优补丁"还是"可复用能力" |
| **模型-harness 共同演化** | 两者联合优化 | RSI 的完整形态 |

## 9. 小结

1. **agent 能力 = 模型 × harness**，harness 是独立于模型规模的性能杠杆，有经验证据支持。
2. **六职责**（观测、上下文、控制、动作、状态、验证/治理）是当前最完整的操作化分解，且各职责都有明确的 RSI 可修改面。
3. **六职责耦合**，改善一层会把风险转移到别处；因此任务是压力剖面，harness 是配置。
4. **harness 层改进成本低、可验证、可回滚**——这解释了为什么 RSI 研究集中于此。
5. **验证/治理层的 RSI 版本与普通版本差别最大**，也是决定整个系统是否可控的层。

参考架构（[04](04-reference-architecture.md)）直接采用六职责作为 L1 的规范骨架。
